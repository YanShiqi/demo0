# 商城与兑换 Token 设计

## 目标与范围

第一版实现一个使用配置货币购买商品的基础商城。商城允许配置多个商品，但只支持 `redemption_token` 一种履约类型：用户购买后获得一个可在现实聊天中自然转赠的不记名 Token，持有完整 Token 的人可以联系超级管理员核销，由超级管理员在线下完成对应事项。

Token 不进入背包，用户通过独立的“我的兑换凭证”页面查看购买记录、Token 掩码、权益、有效期和状态。第一版不实现背包、站内转赠、退款、订单取消、支付充值、商品后台编辑、实体库存和自动履约。未来增加背包时，商城购买流程通过新的履约类型接入，不改变现有兑换凭证结构。

## 核心规则

- Token 不绑定购买账号，不记录现实中的当前持有人，也不判断转赠关系。
- 谁持有完整 Token，谁就可以申请核销；同一个 Token 以第一次成功核销为准。
- 数据库不保存 Token 明文，完整 Token 只在购买成功响应中展示一次。
- 用户离开一次性展示页面后，系统不能再次恢复或展示完整 Token。
- Token 丢失、泄露、过期或被超级管理员作废时不自动退款，也不自动补发。
- 超级管理员可以核销或强制作废有效 Token，两种操作都必须填写备注。
- 商品可以配置有效天数；未配置有效天数表示永不过期。
- 每个商品必须配置用户最多同时持有的未过期、未核销凭证数量。

## 商品配置与图标

商城总配置放在 `config/default.toml` 的 `[shop]` 分组，商品定义放在 `content/shop.toml`。部署环境可用环境变量覆盖商城开关、文件路径、分页数量、备注长度和查询限流等运行参数。所有提交到仓库的配置项必须带中文注释。

商品示例：

```toml
[[products]]
# 稳定商品 ID；创建后不得修改或复用。
id = "milk_tea"
# 商城和凭证中展示的商品名称。
name = "兑换一杯奶茶"
# 说明超级管理员核销后需要履行的事项。
description = "核销后由超级管理员线下履约"
# 商品图标文件名；文件必须位于 static/shop/products/。
icon_file = "milk-tea.webp"
# 购买一次需要扣除的整数货币数量。
price = 10
# Token 自购买时起的有效天数；省略表示永不过期。
valid_days = 30
# 每个用户同时允许持有的有效凭证数量。
max_active_per_user = 1
# 是否在商城上架并允许购买。
enabled = true
# 商城列表中的稳定排序值。
sort_order = 10
```

第一版所有商品的履约类型隐含为 `redemption_token`，订单中仍保存稳定的 `fulfillment_type` 字段，为未来的 `inventory_item` 类型预留扩展点。商品配置修改后重启服务生效；商品下架使用 `enabled = false`，不得复用旧 ID。

图标目录固定为 `static/shop/products/`。配置只接受安全文件名，不接受目录、绝对路径或外部 URL。支持 PNG、WebP 和 JPEG，不支持 SVG 或 GIF。推荐源图为 `512×512`、透明背景、单张不超过 256 KiB；页面使用 `object-fit: contain` 完整展示，非首屏图片使用延迟加载。服务启动时验证文件存在、扩展名、实际图片格式、体积和配置的最大尺寸，发现错误时拒绝加载配置并输出明确错误。订单保存 `icon_file` 快照，仍有历史凭证引用的图标文件不得删除。

## 数据模型

### `shop_orders`

- ULID 主键和购买用户 ID。
- 永久稳定的商品 ID。
- 商品名称、说明、图标文件名、价格、有效天数和履约类型快照。
- 本次实际支付的整数金额。
- 服务端生成的购买请求幂等键，具有唯一约束。
- 创建时间。

订单快照保证商品改名、改价或下架后，历史购买的含义不发生变化。货币流水的 `related_id` 使用订单 ID，幂等键使用稳定的订单购买键。

### `redemption_vouchers`

- ULID 主键和唯一订单 ID。
- 唯一 Token 哈希和只用于展示的 Token 掩码。
- `active / redeemed / cancelled` 状态。
- 可为空的到期时间。
- 核销时间、核销超级管理员 ID 和核销备注。
- 作废时间、作废超级管理员 ID 和作废原因。
- 创建时间。

“已过期”不写入状态字段，而是由 `status = active` 且当前时间不早于 `expires_at` 推导。这样不需要后台定时任务修改凭证，同时仍保留原始状态。

### `voucher_audit_logs`

记录 `created / redeemed / cancelled` 事件、凭证 ID、操作者 ID、时间和备注。审计日志不得保存完整 Token、Token 哈希或用户输入的 Token。

迁移和查询优先使用可移植的标准 SQL。当前时间由 Rust 应用生成并作为参数绑定，不在业务查询中使用 SQLite 时间函数。

## Token 格式与安全

Token 使用操作系统安全随机源生成至少 160 位随机数据，并编码为排除易混淆字符的大写分组字符串，例如：

```text
ZV1-7K3M-P9XD-4R2H-W8QF-N6TY-C5JA-B8VS-T2DE
```

服务端查询时允许忽略大小写、空格和连字符，标准化后校验前缀、长度和字符集，再计算 SHA-256 哈希查询数据库。随机空间足够大，不依赖商品、订单或用户信息产生 Token。Token 不得出现在 URL、Cookie、追踪日志、错误日志、货币备注或审计备注中。

管理员查询使用 POST、现有 CSRF 防护和独立频率限制。查询结果只在完成权限验证后展示。普通管理员不能查询、核销或作废 Token。

## 购买流程与事务

1. 用户访问 `/shop`，服务端分页展示已上架商品、图标、价格、有效期和个人当前可购买状态。
2. 购买确认区明确提示所需货币、不可退款、Token 只显示一次以及丢失不补发。
3. 表单携带 CSRF Token 和服务端生成的一次性购买幂等键；前端只提交商品 ID，不提交可信价格、有效期、持有上限或商品快照。
4. 服务端重新读取商品配置，校验商品上架、用户余额以及该商品未过期 `active` 凭证数量。
5. 在同一数据库事务中创建订单、调用统一货币服务扣款、生成凭证并写入审计记录。
6. 所有操作成功后提交事务，直接返回一次性 Token 展示页面。

并发购买必须在事务中重新检查持有上限。遇到并发写入冲突时回滚并安全重试或提示用户重试，不能依赖页面按钮防重。重复提交相同购买幂等键不得重复扣款或生成 Token，也不得重新展示原 Token。

完整 Token 只存在于首次成功响应的内存和 HTML 中。若成功响应在传输过程中丢失，系统无法恢复该 Token；这属于已确认的“丢失不补发”边界。

## 页面设计

### 商城 `/shop`

使用服务端分页展示商品卡片。卡片包含图标、名称、说明、价格、有效期和购买按钮。达到该商品持有上限或余额不足时禁用购买按钮，并展示具体原因。

### 一次性购买成功页

完整 Token 使用高对比度边框和轻微闪烁提示，明确说明“请立即复制并妥善保存，离开后无法再次查看”，并提供一键复制按钮。系统启用 `prefers-reduced-motion` 时停止动画但保留醒目样式。页面不得通过浏览器缓存长期保存，响应应设置合适的 `Cache-Control`。

### 我的兑换凭证 `/vouchers`

服务端分页展示当前用户购买的凭证，包括商品图标快照、商品名称、Token 掩码、购买时间、到期时间和推导后的状态。页面不提供取消、退款、重发或查看完整 Token 的入口。

### Token 管理 `/admin/vouchers`

仅超级管理员可访问。管理员输入完整 Token 后先查询，不改变状态。结果展示权益、状态、有效期和原购买者，并明确标注“原购买者不代表当前持有人”。查询成功后，可以填写必填备注并确认核销，或填写必填原因并强制作废。

核销与作废使用带 `active` 条件的数据库更新，并在事务中再次检查到期时间。过期、已核销或已作废凭证不能再次操作。成功操作同时更新凭证并写入审计日志。

## 配置与校验

商城运行配置至少包含：功能开关、商品文件路径、商城分页数量、个人凭证分页数量、管理员备注最大长度、Token 查询限流参数、图标最大字节数和最大尺寸。业务代码中的这些限制均读取配置或使用有名称的常量，避免散落数字字面量。

启动时校验商品 ID 唯一且格式稳定，名称和说明长度合法，价格为正整数，有效天数为正整数，持有上限为正整数，排序值合法，图标安全且存在。任何商品配置错误都应指出商品 ID 和具体字段。

## 测试与验收

测试覆盖：

- 多个同类型商品的配置加载、排序、分页和图标校验。
- 余额不足、商品下架、达到持有上限和配置被篡改的购买请求。
- 首次购买、重复提交、并发购买、货币扣款与凭证创建的事务回滚。
- 商品改名、改价或下架后历史订单快照保持不变。
- 完整 Token 只出现在首次成功响应，凭证列表只显示掩码。
- Token 标准化、错误格式、未知 Token、查询限流和日志不泄露。
- 成功核销、重复核销、过期核销、强制作废、重复作废和必填备注。
- 普通用户、普通管理员、超级管理员的权限与 CSRF 校验。
- 动画降级、复制按钮、图片延迟加载及空列表页面结构。

该功能包含商城、订单、货币消费、凭证、安全查询和管理员履约，属于较大更新。实施完成时必须同步更新 `content/updates.toml` 的服务器更新记录。

## 未来背包扩展

商城负责商品展示、订单和扣款，履约模块负责产生具体结果。未来新增 `inventory_item` 履约类型时，在相同购买事务内调用背包服务增加道具，并让货币流水继续关联订单 ID。Token 凭证不迁入账号背包，因为它允许站外自然转赠；背包只承载绑定账号的站内虚拟道具。

第一版不实现通用多重履约。若以后一个商品需要同时生成 Token 和发放背包道具，再将单一 `fulfillment_type` 演进为有序履约列表，并保证所有履约结果与订单扣款处于同一事务。
