# 数据库商品管理与图标自动处理设计

## 背景与目标

现有商城从 `content/shop.toml` 在启动时加载商品，适合最初验证购买与兑换 Token 流程，但新增、改价、上下架和更换图标都需要修改服务器文件并重启。下一阶段将商品目录迁入数据库，由超级管理员在站内管理，所有已提交的变更立即对商城和后续购买生效。

本次继续沿用现有订单、货币消费和兑换 Token 设计，只改变商品来源并增加全站限售、商品审计和图标自动处理。第一版仍只支持 `redemption_token` 履约，不实现退款、补发、通用库存预占、组合商品或背包道具。

## 方案选择

数据库是商品的唯一事实来源。商城列表和购买事务直接查询数据库，不增加内存商品缓存，避免后台修改后出现缓存失效或多份配置互相覆盖的问题。`content/shop.toml` 不再作为运行时商品来源；`config/default.toml` 只保留商城开关、分页、限流和图片处理边界。

当前仓库中的 `content/shop.toml` 没有实际商品，因此不实现旧目录自动导入。若部署环境自行配置过商品，应在升级前备份，并在新后台中使用原商品 ID 完成一次性人工迁移。迁移旧 ID 时以同 ID 的历史订单数量初始化已售数量，避免切换商品来源后绕过限售规则。数据库后台新建后又被永久删除的 ID 则由审计记录标记为已使用，之后不得复用。

## 数据模型

### `shop_products`

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定商品 ID；小写字母、数字、下划线和连字符，创建后不可修改或复用 |
| `name` / `description` | 商城展示名称和线下履约说明 |
| `icon_storage_name` / `icon_media_type` | 服务器生成的图标存储名和可信媒体类型 |
| `price` | 购买需要扣除的正整数货币数量 |
| `valid_days` | 可为空的 Token 有效天数；为空表示永不过期 |
| `max_active_per_user` | 单个用户同时持有此商品有效凭证的上限 |
| `total_limit` | 可为空的全站限售数量；为空表示不限售 |
| `sold_count` | 已成功购买数量，只能由购买事务增加 |
| `enabled` | 是否在商城展示并允许购买 |
| `sort_order` | 商品列表排序值，数值越小越靠前 |
| `created_by_user_id` / `updated_by_user_id` | 创建和最近修改的超级管理员 |
| `created_at` / `updated_at` | 由 Rust 生成并绑定的 UTC RFC 3339 时间 |

`price`、`valid_days`、`max_active_per_user` 和非空的 `total_limit` 必须为正整数。`total_limit` 不得低于 `sold_count`。新建商品若已存在同 ID 历史订单，`sold_count` 使用这些订单的数量，且配置的限售数量不得低于该值。

### `shop_product_audit_logs`

审计表保存 ULID 主键、稳定商品 ID、`created / updated / enabled / disabled / deleted` 操作、操作者、修改前后快照和创建时间。快照由 Rust 序列化为普通文本，业务 SQL 不调用 SQLite JSON 函数。审计记录不依赖商品外键，因此商品被永久删除后记录仍然存在；快照不包含图片二进制内容。

迁移和查询继续优先使用可移植标准 SQL。不可避免的 SQLite 并发配置仍集中在数据库初始化层，不在商品业务查询中加入 SQLite 时间或 JSON 方言。

## 商品生命周期

- 超级管理员可以新增、编辑、上架、下架商品。
- 商品 ID 创建后只读；名称、说明、价格、有效期、持有上限、限售量、排序和图标可以修改。
- 修改只影响后续购买。现有 `shop_orders` 继续保存购买时的商品名称、说明、图标、价格和有效期快照。
- 无任何历史订单的商品可以永久删除，并写入删除审计。
- 已有历史订单的商品不能物理删除，只能下架。
- 下架商品不在公开商城展示，购买端点也必须拒绝；历史订单和兑换凭证仍可查看与核销。
- 降低每用户持有上限不会撤销已有凭证；已经超过新上限的用户在有效凭证数量下降前不能再次购买。

后台路由位于 `/admin/shop/products`，入口放入现有“管理”下拉菜单。列表展示状态、价格、已售数量、全站限售量、每用户上限和排序，并提供新增、编辑、上架、下架及符合条件时的删除操作。编辑时不上传新图标即保留现有图标，选择文件后先在浏览器预览。

只有超级管理员可以读取或修改商品后台；普通管理员、普通用户和匿名访问者均不能访问。所有写操作使用 POST、会话权限校验和 CSRF 防护，不通过 GET 或查询参数改变状态。

## 全站限售与购买事务

`total_limit` 为空表示不限售。达到上限后商城显示“已售罄”并禁用购买按钮，但服务端仍必须在事务中裁决，不能信任页面状态。

购买时，服务端只接收商品 ID、CSRF Token 和幂等请求键，并在事务中重新读取最新商品。事务依次完成：

1. 校验商品存在且已上架。
2. 锁定购买用户，检查幂等请求、余额和个人有效凭证上限。
3. 使用带商品 ID、上架状态和剩余限售条件的更新原子增加 `sold_count`。
4. 使用数据库中的当前商品值创建订单快照。
5. 扣除货币、创建兑换凭证并写入凭证审计。
6. 所有步骤成功后提交事务并返回一次性完整 Token。

销量增加、货币扣除、订单和凭证创建属于同一事务；任一步失败必须整体回滚。购买事务失败不计销量。凭证之后过期、核销或被取消均不恢复销量。下架和购买同时发生时，以先成功提交的事务为准：已经提交的购买有效，之后的购买被拒绝。

## 图标上传与自动处理

图标保存在 `data/shop/product-icons/`，不提交 Git。文件名使用服务器生成的 ULID 和可信扩展名，不使用上传文件名、路径或外部 URL。商品图标通过现有受控图片路由提供，订单继续保存图标存储名快照；新图标使用新文件名，使浏览器缓存不会阻止修改立即显示。

允许 PNG、JPEG、WebP 和 GIF，不允许 SVG 或未知格式。所有边界均从带中文注释的配置项读取，默认值为：

- 原始上传最大 5 MiB。
- 原始图片最大 4096×4096。
- GIF 最多 120 帧。
- GIF 解码总像素不超过 80,000,000。
- 输出文件最大 1 MiB。
- 依次尝试 512、384、256 像素的最大边长。

静态图片按比例缩小并统一编码为 WebP，保留透明通道。GIF 必须完整遍历和验证所有帧，再逐帧缩放并重新编码，保留动画帧延迟和循环方式。处理结果超过 1 MiB 时按配置的候选尺寸继续缩小；降到 256 像素后仍超限则拒绝上传，不能静默转换为静态首帧。

图片解码和重新编码在专用阻塞任务中执行，避免阻塞异步请求线程。表单提交后禁用重复提交并显示“正在处理图片”。服务端请求体仍保留原始上传硬上限，因为自动压缩发生在文件接收和解码之后，不能安全接受无限大小输入。

处理结果先写入同目录临时文件。图片落盘、商品写入和审计任一步失败时清理本次临时或正式新文件，不产生可见的半成品商品。服务启动时只清理明确的过期 `.tmp` 文件，不猜测删除正式图片。

更换图标后，若旧图标仍被 `shop_orders` 快照引用则继续保留；没有商品或订单引用时才删除。删除无订单商品时同样只删除已确认无引用的图标。商城保持服务端分页和图片延迟加载，限制单页同时播放的 GIF 数量。

## 校验与错误反馈

- 重复或格式错误的商品 ID、空名称、空说明和非法整数在原表单显示明确错误。
- 创建商品时同时检查现有商品和商品审计；已经由数据库后台创建过的 ID 即使商品已删除也不能复用。只有没有商品审计记录的旧 TOML ID 可以按迁移规则接续历史订单。
- 编辑商品时以数据库最新值为准；限售量低于已售数量时拒绝保存并显示当前已售数量。
- 图片扩展名不作为可信依据，必须核对文件内容识别出的格式。
- 损坏 GIF、超出帧数、解码像素或处理后体积限制时，错误说明具体限制，不保存商品变更。
- 商品在页面打开后被下架、删除或售罄时，购买请求返回对应业务提示，不扣款、不生成订单。
- 重复购买请求继续遵守现有幂等规则，不重复增加销量、扣款或展示完整 Token。

## 配置调整

`ShopConfig` 移除运行时 `products_file` 和内存 `products`。保留商城开关、商城分页、凭证分页、管理员备注长度和 Token 查询限流，并增加图标存储目录、原始上传上限、输入尺寸、GIF 帧数、解码总像素、输出体积和候选缩放尺寸配置。

所有新配置同步写入 `config/default.toml` 和 `.env.example`，每项带中文用途说明。应用启动时创建图标目录并验证所有数值为正、候选尺寸按降序排列且不为空。`content/shop.toml` 不再被应用读取，可在实现完成后删除或仅作为历史设计参考移出运行配置。

## 测试与验收

测试至少覆盖：

- 新迁移的字段、约束、索引和审计表。
- 超级管理员成功管理商品，以及其他角色和 CSRF 请求被拒绝。
- 新增、改价、修改限售、上下架和删除立即反映在公开商城及购买端点。
- 无订单商品可删除、有订单商品只能下架，历史订单快照保持不变。
- 不限售、临界最后一份、售罄和并发购买不会超售。
- 购买失败时销量、货币、订单和凭证全部回滚；幂等重试不重复计数。
- 静态图缩放与 WebP 输出，GIF 动画、延迟和循环保留，以及文件、尺寸、帧数、解码像素和输出体积限制。
- 图标更换后的缓存更新、历史图标保留、无引用图标清理和处理失败清理。
- 配置文件每项具备中文注释，新增业务 SQL 不使用可避免的 SQLite 方言。

实现完成后运行 `cargo fmt --check`、`cargo test` 和 `cargo clippy --all-targets --all-features -- -D warnings`。本功能包含数据库迁移、权限变化、商品管理、库存和图片处理，属于大型用户功能，届时必须在 `content/updates.toml` 新增日期为 2026-08-14、版本为 `0.1.5` 的服务器更新记录。

## 后续扩展

本设计只为商品目录增加数据库管理和限售，不改变现有 `redemption_token` 履约。未来增加背包道具时，可以在 `shop_products` 增加或关联履约配置，并复用相同的商品管理、限售和订单事务边界。若需要补货式库存、预约库存或取消订单返还库存，应作为独立版本设计，不能直接改变本版“成功购买即永久计入销量”的规则。
